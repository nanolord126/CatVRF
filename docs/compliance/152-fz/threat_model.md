## 1. Общие сведения

### 1.1. Характеристика ИСПДн

**Наименование системы:** CatVRF — AI-powered Healthcare Marketplace  
**Тип системы:** Многотенантная SaaS-платформа маркетплейса медицинских услуг  

**Категории обрабатываемых персональных данных:**

- **Иные ПДн:**
  - ФИО
  - Адрес электронной почты (email)
  - Номер телефона
  - Адрес доставки
  - Дата рождения
  - Пол

- **Биометрические ПДн:**
  - Изображение лица (Face ID)
  - Данные liveness-проверки
  - Поведенческие биометрические данные (клавиатурный почерк, динамика движений мыши, жесты)
  - Голосовые биометрические данные

- **Специальные категории (при KYB):**
  - Паспортные данные директора бизнеса
  - ИНН, ОГРН

**Объём субъектов:** > 100 000  
**Количество тенантов:** > 1 000  
**Локализация данных:** Российская Федерация  

### 1.2. Контуры обработки

1. **Central DB** — центральная база данных с метаданными тенантов, уникальными контактами, согласиями
2. **Tenant-specific DB** — тенант-специфические базы данных с клиентскими данными, заказами, поведенческими профилями
3. **Frontend (Vue/Livewire)** — сбор поведенческих сигналов
4. **API** — REST API для интеграций
5. **Filament** — админ-панель для staff/super-admin

### 1.3. Обоснование уровня защищённости УЗ-3

Согласно Постановлению Правительства РФ № 1119 от 01.11.2012:

- **Количество субъектов:** > 100 000 (требует УЗ-3)
- **Биометрические ПДн:** обрабатываются (требует УЗ-3)
- **Категории данных:** биометрические + иные ПДн в большом объёме
- **Потенциальный ущерб:** критический при утечке биометрии

**Вывод:** УЗ-3 является обязательным уровнем защищённости для ИСПДн CatVRF.

## 2. Модель нарушителя

### 2.1. Внешний нарушитель

**Тип:** Внешний нарушитель  
**Мотивация:** Финансовая выгода, продажа баз, конкуренция, хантинг клиентской базы  
**Возможности:**
- SQL injection
- API abuse (credential stuffing, token replay)
- Эксплуатация уязвимостей (Laravel, Livewire, Filament)
- Phishing
- Бот-скрапинг
- Exploit уязвимостей (zero-day)

**Ресурсы:** Средние/высокие (ботнеты, zero-day)  
**Уровень возможностей:** 3 (базовый) — 1 (высокий) по шкале ФСТЭК  
**Актуальность:** Высокая  

### 2.2. Внутренний нарушитель (Insider)

**Тип:** Внутренний нарушитель  
**Мотивация:** Личная выгода, месть, сговор  
**Возможности:**
- Легитимный доступ через Filament/API
- Bulk export данных
- Raw queries к базе данных
- Hunting по контактам (email/phone patterns) внутри Tenant
- Несанкционированный доступ после compromised staff аккаунта

**Ресурсы:** Низкие-средние (но высокий уровень доступа)  
**Уровень возможностей:** 2 (средний) по шкале ФСТЭК  
**Актуальность:** Очень высокая  

### 2.3. Случайный нарушитель

**Тип:** Случайный нарушитель  
**Мотивация:** Ошибка администратора, потеря устройства, неправильная конфигурация  
**Возможности:**
- Misconfiguration
- Accidental data exposure
- Backup leaks

**Ресурсы:** Низкие  
**Уровень возможностей:** 3 (базовый) по шкале ФСТЭК  
**Актуальность:** Низкая-средняя

### 3.3. Сценарии реализации угроз

#### Сценарий 1: Insider data exfiltration via Filament bulk export

**Описание:** Сотрудник с ролью moderator использует Filament bulk export для выгрузки 10k клиентских email/phone.

**Этапы:**
1. Сотрудник авторизуется в Filament с легитимными учётными данными
2. Переходит в раздел пользователей
3. Инициирует bulk export всех контактов
4. ExportGuard блокирует операцию (> 1000 записей)
5. Инцидент логируется в ClickHouse
6. InsiderThreatService создаёт alert

**Меры защиты:**
- ExportGuard с лимитами
- Rate limiting
- InsiderThreatService
- Immutable audit logging

#### Сценарий 2: External attacker via compromised staff token

**Описание:** Внешний хакер через phishing получает staff токен и пытается выполнить hunting по клиентской базе.

**Этапы:**
1. Phishing атака на сотрудника
2. Кража staff токена
3. Использование токена для API запросов
4. Попытка массового доступа к контактам
5. BehavioralBiometrics детектирует аномалии
6. Акаунт блокируется

**Меры защиты:**
- Behavioral Biometrics
- FraudControlService
- Multi-factor authentication
- Session monitoring

#### Сценарий 3: Cross-tenant leakage via misconfigured scope

**Описание:** Ошибка в TenantScope приводит к тому, что клиент одного Tenant видит данные другого.

**Этапы:**
1. Разработчик вносит ошибку в TenantScope
2. Деплой в production
3. Клиент Tenant A видит данные Tenant B
4. TenantIsolationMiddleware блокирует запрос
5. Инцидент логируется
6. Автоматический rollback

**Меры защиты:**
- TenantIsolationMiddleware
- Global scopes
- Row-level security
- Automated testing

## 7. Обновление модели угроз

### 7.1. Периодичность обновления

- **Обязательное:** Минимум раз в 3 года (Методика ФСТЭК 2021)
- **Рекомендуемое:** Ежеквартально
- **Автоматическое:** При появлении новых релевантных угроз из БДУ

### 7.2. Основания для обновления

- Добавление новой биометрии (например, iris recognition)
- Рост объёма субъектов (> 100 000 → > 1 000 000)
- Изменение архитектуры системы
- Появление новых критических уязвимостей
- Изменение законодательства

### 7.3. Процесс обновления

1. Запуск `SyncFstecBduJob` для получения актуальных угроз
2. Анализ новых угроз и уязвимостей
3. Обновление матрицы рисков
4. Проверка достаточности мер защиты
5. Добавление новых мер при необходимости
6. Обновление документа
7. Утверждение ответственным за ИБ
8. Хранение версии в Git
